## Q3. 바인드 마운트로 오류 로그 추출 (8점)

호스트 data 폴더를 연결해야 결과가 컨테이너 종료 후에도 남습니다. grep은 대소문자를 구별하고 sort 후 uniq로 떨어져 있는 중복도 제거합니다. >는 덮어쓰기이므로 재실행 결과가 누적되지 않습니다. 매치가 없는 grep의 종료 코드 1은 이 파이프라인에서 오류 데이터가 없음을 뜻하며 마지막 uniq는 빈 파일을 만듭니다.

배점: 마운트 3 / 필터·정렬·중복제거·덮어쓰기 3 / 재실행·빈 입력 확인 2

파일: answers/q03.txt

~~~text
docker run --rm -v "${PWD}/data:/data" alpine:3.21.3 sh -c 'grep "ERROR" /data/system.log | sort | uniq > /data/errors.txt'
docker run --rm -v "${PWD}/data:/data:ro" alpine:3.21.3 cat /data/errors.txt
docker run --rm -v "${PWD}/data:/data" alpine:3.21.3 sh -c 'grep "ERROR" /data/system.log | sort | uniq > /data/errors.txt'
docker run --rm -v "${PWD}/data:/data:ro" alpine:3.21.3 cat /data/errors.txt
docker run --rm -v "${PWD}/data:/data" alpine:3.21.3 sh -c 'grep "ERROR" /data/empty.log | sort | uniq > /data/empty-errors.txt'
docker run --rm -v "${PWD}/data:/data:ro" alpine:3.21.3 wc -c /data/empty-errors.txt
~~~

## Q6. 콘솔 메시지 송수신 (8점)

새 토픽·단일 파티션으로 순서를 명확히 했습니다. --partition 0으로 직접 읽고 --from-beginning으로 시작 위치를 지정하여 기존 그룹의 커밋 상태에 의존하지 않습니다. --max-messages 3은 세 메시지를 받으면 종료하게 합니다. 부족하면 timeout으로 끝나므로 stderr와 건수를 함께 확인합니다.

배점: 토픽 생성 2 / 프로듀서·데이터 2 / 처음부터·파티션·건수 제한 4

## Q7. 단일 브로커 명령 디버깅 (7점)

복제본 수는 파티션 수와 별개입니다. 한 브로커에 같은 파티션의 복제본 3개를 두는 것으로 RF=3을 만들 수 없습니다. Java CLI 속성 batch.size와 Python 생성자 batch_size의 표기를 구별합니다. 이 문제는 Java 콘솔 속성입니다.

배점: A와 복제·파티션 구분 3 / B 및 바이트 단위 2 / C 밀리초 2

파일: answers/q07.txt

~~~text
docker compose exec kafka kafka-topics --bootstrap-server localhost:9092 --create --topic mk-debug --partitions 3 --replication-factor 1
# A: 브로커 1대이므로 RF=3은 불가. 파티션 수와 복제계수는 별개이다.
docker compose exec kafka kafka-console-producer --bootstrap-server localhost:9092 --topic mk-debug --producer-property batch.size=512
# B: 속성 이름은 batch.size이며 512의 단위는 bytes이다. 512개 메시지가 아니다. 실행 확인 뒤 Ctrl+C.
docker compose exec kafka kafka-configs --bootstrap-server localhost:9092 --alter --topic parcel-events --add-config retention.ms=1800000
# C: 30 * 60 * 1000 = 1800000 ms. 1800 ms는 1.8초이다.
~~~

## Q8. Admin API로 안전한 토픽 준비 (8점)

원본 실습의 삭제 후 고정 2초 대기 패턴 대신 기존 토픽 보존 방식을 요구했습니다. 비동기 삭제가 2초 안에 끝난다고 보장할 수 없기 때문입니다. 없는 토픽만 리스트로 생성하고 두 번째 실행은 아무것도 만들지 않습니다. 실제 API 호출과 예외는 테스트 대역으로 검사했습니다.

배점: 현재 목록·차집합 3 / NewTopic·생성 3 / 반환·재실행 2

파일: tasks/q08_admin.py

~~~text
"""Q08 reference solution."""
TOPICS = {"mk-orders": 3, "mk-input": 1, "mk-output": 1}

def prepare_topics(admin):
    from kafka.admin import NewTopic
    existing = set(admin.list_topics())
    missing = sorted(set(TOPICS) - existing)
    if missing:
        admin.create_topics([NewTopic(name=n, num_partitions=TOPICS[n],
                                      replication_factor=1) for n in missing])
    return missing
~~~

## Q9. 키를 가진 Python 프로듀서 (10점)

문자열 키·값은 각각 UTF-8로 직렬화합니다. text가 빈 문자열이어도 삭제하지 않습니다. send는 비동기이므로 Future.get으로 오류를 확인하고 마지막 flush로 버퍼의 완료를 기다립니다. 여기서는 이해와 실패 확인을 위해 건별 대기하므로 고성능 배치 예제는 아닙니다.

배점: 주소·키/값 직렬화 3 / 키·값·토픽·빈 값 4 / 결과 확인·flush·건수 3

파일: tasks/q09_producer.py

~~~text
"""Q09 reference solution."""
def make_producer(factory, bootstrap):
    return factory(bootstrap_servers=bootstrap,
                   key_serializer=str.encode, value_serializer=str.encode)

def send_records(producer, records):
    count = 0
    for record in records:
        producer.send("mk-orders", key=record["store"], value=record["text"]).get(timeout=10)
        count += 1
    producer.flush()
    return count
~~~

## Q10. 컨슈머 설정과 디코딩 (7점)

earliest는 유효한 커밋 위치가 없을 때 적용하는 초기화 정책입니다. 자동 커밋과 그룹 ID는 제공 요구에 맞춥니다. bytes를 해독하고 null key는 예외 없이 None으로 보존합니다. 파티션·오프셋은 각 메시지의 메타데이터에서 읽습니다.

배점: 생성자 설정 3 / 디코딩·null·메타데이터 3 / 빈 입력 1

파일: tasks/q10_consumer.py

~~~text
"""Q10 reference solution."""
def make_consumer(factory, topic, bootstrap, group):
    return factory(topic, bootstrap_servers=bootstrap, group_id=group,
                   auto_offset_reset="earliest", enable_auto_commit=True,
                   consumer_timeout_ms=10000)

def collect(consumer):
    result = []
    for message in consumer:
        result.append({"key": None if message.key is None else message.key.decode("utf-8"),
                       "value": message.value.decode("utf-8"),
                       "partition": message.partition, "offset": message.offset})
    return result
~~~

## Q11. 입력 토픽을 정제해 출력 토픽으로 전달 (10점)

공백 제거 후 빈 값만 건너뛰며 한글도 UTF-8로 처리합니다. 상위 실행기가 소비자와 생산자를 닫습니다. 이 자동 커밋 입문 파이프라인은 입력 오프셋 커밋과 출력 전송의 원자성을 제공하지 않아 장애 때 재처리·누락 가능성이 있습니다. 수동 커밋과 트랜잭션 구현은 이번 범위에서 제외했습니다.

배점: 해독·공백·대문자 3 / 빈 값·오류 2 / 출력 토픽·건수·전송 확인·flush 5

파일: tasks/q11_pipeline.py

~~~text
"""Q11 reference solution."""
def transform(raw):
    value = raw.decode("utf-8").strip().upper()
    return value if value else None

def relay(consumer, producer):
    count = 0
    for message in consumer:
        value = transform(message.value)
        if value is not None:
            producer.send("mk-output", value=value).get(timeout=10)
            count += 1
    producer.flush()
    return count
~~~

## Q12. 출력과 장애 조건 해석 (10점)

정답은 answers/q12.md와 같습니다. 레코드 개수와 최신 오프셋, 복제계수와 파티션 수, 클러스터 관리 방식과 데이터 복제를 분리해 설명하면 됩니다. Java와 Python 클라이언트의 분배 정책을 혼용하지 않습니다.

배점: 그룹 3 / 오프셋 조건 2 / RF·KRaft 3 / 클라이언트별 분배 2

파일: answers/q12.md

~~~text
# Q12 정답

1. 최대 3개가 담당하고 최소 1개가 유휴이다. 같은 그룹의 한 파티션은 안정된 할당에서 한 컨슈머만 담당한다. 파티션별 메시지 건수나 처리시간이 균등해진다는 뜻은 아니다. 다른 그룹은 독립적으로 읽을 수 있다.

2. 주어진 초기 조건에서는 offset 0~4의 5건이다. 5는 최신 끝 위치(다음에 기록될 오프셋)이지 일반적인 현재 메시지 건수가 아니다. 시작이 3이면 연속한 비압축 로그의 남은 구간은 3,4의 2건이다. 압축 등으로 오프셋에 구멍이 있으면 단순 차이도 정확한 레코드 수가 아니다.

3. 불가능하다. RF=1이면 ISR에 리더 자신만 있으며 acks=all도 별도 복제본을 만들어 주지 않는다. KRaft는 메타데이터·클러스터 관리 방식이고 데이터 복제계수와 별개다. RF-1만으로 무조건 쓰기 가용성이나 무손실을 보장할 수 없다.

4. 즉시 오류라고 할 수 없다. Java 콘솔 클라이언트의 키 없는 분배는 배치·타이밍·설정의 영향을 받는다. 소량의 균등 분산이나 특정 분포를 강제하지 않는다. kafka-python 2.0.4의 기본 키 없는 파티셔너는 가능한 파티션 중 무작위 선택이므로 Java의 sticky 설명을 그대로 적용하면 안 된다. 같은 키도 파티션 수·직렬화·파티셔너가 유지된다는 조건이 필요하다.
~~~
