## Q02. Docker 기본 명령 (8점)

```
docker run --name hello-test hello-world
docker ps -a
docker rm hello-test
docker images
docker run -it --name devbox python:3.10-slim bash
pwd                         # → /
echo "inside devbox" > note.txt
cat note.txt
python -c "print(6 * 7)"    # → 42
exit
docker start -ai devbox
cat note.txt                # → inside devbox (유지됨)
exit
docker stop devbox
docker rm devbox
```

- [9] `docker start` 는 **기존 컨테이너**를 다시 실행하므로 쓰기 계층이 남아 있다. `docker rm` 으로 지운 뒤 `docker run` 하면 이미지에서 **새 컨테이너**가 만들어져 note.txt가 없다.
- 감점: `docker ps`(‑a 없음)로는 Exited 컨테이너가 안 보임. `-it` 없이 `bash` 를 실행하면 바로 종료됨. `docker start devbox` 만 쓰면 백그라운드로 시작되어 터미널에 붙지 않음(`-ai` 필요).
- 실측: `-dit` + `exec` 로 같은 흐름을 재현해 pwd `/`, 42, 재시작 후 note 유지, rm 후 새 run에는 note 없음 확인.

## Q03. Flask 이미지 (12점)

```dockerfile
FROM python:3.10-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .
CMD ["python", "app.py"]
```
- `requirements.txt`: `flask`
- `app.py` 오류 수정: `app.run(host="0.0.0.0", port=5000)`
- 명령: `docker build -t delivery-api .` → `docker run -d -p 8000:5000 --name delivery-api-container delivery-api` → `docker ps` → `curl http://localhost:8000/`, `/status` → `docker stop`/`docker rm delivery-api-container`

해설
- host를 안 주면 Flask는 `127.0.0.1` 에서만 받는다. 실측 로그 `* Running on http://127.0.0.1:5000`, 컨테이너는 `Up` 인데 호스트 요청은 실패.
- `-p 호스트:컨테이너` 순서. `-p 5000:8000` 으로 쓰면 접속 불가.
- `build` 끝의 `.`(빌드 컨텍스트)를 빠뜨리면 오류.
- requirements를 app.py보다 먼저 복사하는 이유: app.py만 바뀌면 pip 설치 레이어를 캐시로 재사용.

## Q04. 볼륨 마운트 로그 감시 (8점)

```dockerfile
FROM python:3.10-slim
WORKDIR /app
COPY watch_log.py .
CMD ["python", "watch_log.py"]
```
```
docker build -t order-watcher .
docker run --name order-watcher-c -v $(pwd)/order.log:/logs/order.log order-watcher
echo "[OK] order-101 delivered" >> order.log
echo "[FAIL] order-102 address not found" >> order.log
docker rm order-watcher-c
```
- 오류 수정: exec 형식 CMD는 **배열 원소 하나가 실행 파일 하나**다. `["python watch_log.py"]` 는 `python watch_log.py` 라는 이름의 실행 파일을 찾는다. 실측 오류: `exec: "python watch_log.py": executable file not found in $PATH` (빌드는 성공).
- `-v 호스트경로:컨테이너경로`. 호스트 쪽은 절대경로여야 하므로 `$(pwd)` 사용.
- 감시는 실행 이후 추가된 줄만 출력(`f.seek(0, 2)`)하므로 `[INIT]` 줄은 나오지 않는다.
- [5] `>` 는 파일을 비우고 다시 쓴다. 실측: `>` 로 한 줄을 쓴 뒤에는 새 출력이 나오지 않았다(읽기 위치가 이전 파일 끝에 머묾). 환경에 따라 일부 글자만 출력될 수도 있다.
- `-d` 로 실행했다면 `docker logs order-watcher-c` 로 같은 출력을 볼 수 있다(대안 정답 인정).

## Q05. Compose (10점)

```yaml
services:
  web:
    image: nginx:alpine
    container_name: delivery-web
    ports:
      - "8081:80"
    volumes:
      - ./index.html:/usr/share/nginx/html/index.html
  api:
    image: alpine
    container_name: delivery-api
    command: ["sleep", "infinity"]
```
```
docker compose up -d
docker compose ps
docker compose exec api ping -c 3 web
docker compose exec api apk add curl
docker compose exec api curl http://web
curl http://localhost:8081
docker compose down
```
- `ping web`(‑c 없이, Ctrl+C로 종료)도 정답 인정. `exec` 뒤에는 **서비스 이름**(api)을 쓴다.
- [8] 실패(실측 curl 종료코드 7 = 연결 실패). 컨테이너 안의 localhost는 그 컨테이너 자신이며 8081은 호스트의 포트다. 같은 네트워크에서는 `http://web`(web:80).
- `version: "3"` 줄은 최신 Compose에서 obsolete 경고만 나오고 무시된다.

## Q06. Kafka 토픽 관리 (10점)

```
docker compose up -d
docker compose ps
docker compose exec kafka kafka-topics --create --topic delivery-status --bootstrap-server localhost:9092 --partitions 3 --replication-factor 1
docker compose exec kafka kafka-topics --list --bootstrap-server localhost:9092
docker compose exec kafka kafka-topics --describe --topic delivery-status --bootstrap-server localhost:9092
docker compose exec kafka kafka-configs --alter --topic delivery-status --bootstrap-server localhost:9092 --add-config retention.ms=1800000
docker compose exec kafka kafka-configs --describe --topic delivery-status --bootstrap-server localhost:9092
docker compose exec kafka kafka-topics --create --topic delivery-temp --bootstrap-server localhost:9092 --partitions 1 --replication-factor 1
docker compose exec kafka kafka-topics --delete --topic delivery-temp --bootstrap-server localhost:9092
docker compose exec kafka kafka-topics --list --bootstrap-server localhost:9092
```
- 30분 = 30 × 60 × 1000 = **1800000** ms. 실측 출력: `Completed updating config for topic delivery-status.` / `retention.ms=1800000 sensitive=false synonyms={DYNAMIC_TOPIC_CONFIG:retention.ms=1800000}`
- 옵션 순서는 바뀌어도 된다.

[8] 디버깅 — 실측 반응

| | 원인 | 실측 메시지 | 수정 |
|---|---|---|---|
| (A) | Docker 환경에서 `./bin/*.sh` 사용 + `--patitions` 철자 | `stat ./bin/kafka-topics.sh: no such file or directory` / `patitions is not a recognized option` | `docker compose exec kafka kafka-topics --create --topic delivery-log ... --partitions 2 --replication-factor 1` |
| (B) | `--topic` 누락 | **오류 없이 실행됨.** 토픽 이름이 무시되고 전체 토픽을 조회 | `... --describe --topic delivery-status ...` |
| (C) | 브로커 1대에 RF 3 | `The target replication factor of 3 cannot be reached because only 1 broker(s) are registered.` | `--replication-factor 1` |
| (D) | 설정 변경은 kafka-configs | `add-config is not a recognized option` | `docker compose exec kafka kafka-configs --alter ... --add-config retention.ms=600000` |

(B)처럼 오류 없이 엉뚱한 결과가 나오는 경우가 가장 놓치기 쉽다. (A)와 (D)는 실습자료 answer 파일에 실제로 있던 실수(`--patitions`, kafka-topics로 alter)를 응용했다.

## Q07. 콘솔 프로듀서·컨슈머 (10점)

```
docker compose exec kafka kafka-topics --create --topic order-events --bootstrap-server localhost:9092 --partitions 3 --replication-factor 1
docker compose exec kafka kafka-console-producer --topic order-events --bootstrap-server localhost:9092
docker compose exec kafka kafka-console-consumer --topic order-events --from-beginning --bootstrap-server localhost:9092
docker compose exec kafka kafka-console-consumer --topic order-events --bootstrap-server localhost:9092 --from-beginning --partition 0
(… --partition 1, --partition 2)
docker compose exec kafka kafka-get-offsets --bootstrap-server localhost:9092 --topic order-events
docker compose exec kafka kafka-console-producer --topic order-events --bootstrap-server localhost:9092 --producer-property batch.size=512
```
- (a) 0개 / 5개 / 0개
- (b) 누적 오프셋의 차이: 0번 7-0=7, 1번 12-5=7, 2번 6-0=6 → 합계 20. **12를 그대로 쓰면 오답**(누적값).
- (c) 키 없는 메시지는 Sticky 파티셔너가 배치가 찰 때까지 한 파티션에 몰아 보낸다. 기본 batch.size 16384B는 작은 메시지 5개로 채워지지 않는다. 512B로 줄이면 300B짜리 메시지 1~2개로 배치가 차서 파티션이 자주 바뀐다.
- 실측(같은 데이터): small 5개 → `{0:0, 1:0, 2:5}`(한 파티션 집중), batch.size=512 의 large 20개 → `{0:10, 1:4, 2:6}`(분산). 비교로 같은 20개를 기본 batch.size로 보내면 `{0:20, 1:0, 2:0}`.
- `kafka-get-offsets` 출력 `토픽:파티션:오프셋`. 오프셋은 다음에 쓸 위치이므로, 시작 오프셋 0인 새 토픽에서는 그 파티션의 메시지 개수와 같다.
- 대화형 입력 대신 `docker compose exec -T kafka kafka-console-producer ... < ../q07/small_messages.txt` 처럼 파일을 넣는 방법도 있다(`-T`: 가상 터미널 없이 표준입력 연결). 실습 범위 밖이므로 참고만.

## Q08. Python 키 기반 프로듀서·컨슈머 (12점)

빈칸: `"localhost:9092"`, `list_topics`, `3`, `1`, `create_topics`, `close`, `str.encode` ×2, `i % len(regions)`, `send`, `key`, `value`, `flush` / 컨슈머: `"region-orders"`, `"earliest"`, `"region-checker"`, `consumer`, `decode("utf-8")` ×2, `partition`

- 오류 수정: `admin_client.delete_topics([topic_name])`. `delete_topics` 는 토픽 이름의 **리스트**를 받는다. 문자열을 넘기면 글자 하나하나를 토픽 이름으로 본다. 실측 오류: `InvalidRequestError ... DeleteTopicsRequest_v3(topics=['r', 'e', 'g', 'i', ...])`. 토픽이 없는 첫 실행에서는 이 줄이 실행되지 않아 드러나지 않는다.
- 같은 키 → 같은 파티션: `hash(key) % 파티션 수`. 실측: seoul→0, daejeon→1, ulsan→2 (kafka-python 2.0.4 기본 파티셔너, murmur2).
  - 참고: 출제 중 seoul·busan·gwangju 로 시험했더니 세 키가 모두 파티션 0으로 갔다. **키가 다르다고 파티션이 꼭 다른 것은 아니다**(해시 충돌). "같은 키 → 같은 파티션"은 보장, "다른 키 → 다른 파티션"은 보장되지 않는다.
- `flush()` 를 빼면 짧은 스크립트가 끝날 때 버퍼의 메시지가 전송되지 않을 수 있다(이 노트북은 `future.get()` 으로 각 전송을 기다리므로 실제로는 전송되지만, 요구사항상 flush는 필수).
- 컨슈머를 같은 그룹으로 다시 실행하면 0건(실측). Q10 (5) 참고.

## Q09. 변환 파이프라인 (10점)

- q09_1: `list_topics`, `delete_topics`, `create_topics`, `input_topic`, `output_topic`, `value_serializer`, `input_topic`, `message`, `flush`
- q09_2: `"raw-orders"`, `"earliest"`, `True`, `"transformer-group"`, `str.encode`, `decode("utf-8")`, `strip`, `not text`, `continue`, `upper`, `flush`
- q09_2 오류 수정: `producer.send("clean-orders", value=transformed)`. `value_serializer=str.encode` 가 이미 bytes로 바꾸므로 직접 `.encode()` 하면 bytes를 다시 str.encode에 넣게 된다. 실측: `TypeError: descriptor 'encode' for 'str' objects doesn't apply to a 'bytes' object`
- q09_3: `"clean-orders"`, `"localhost:9092"`, `"earliest"`, `"output-checker"`, `consumer`, `decode("utf-8")`
- 실측: `forwarded=4`, `Skipped empty message` 1회, `results: ['COFFEE', 'TEA', 'LATTE', 'SANDWICH'] count: 4`. 1→2→3을 같은 그룹 ID로 다시 실행해도 같은 결과였다(1번이 토픽을 지우고 다시 만들어 이전 커밋 오프셋이 사라짐).

## Q10. 서술형 채점 기준 (각 2점)

| | 핵심어(1점씩) |

| (5) | 커밋된 오프셋부터 읽어서 0건, earliest는 커밋이 없을 때만 / 새 group_id. 같은 그룹 2개 + 파티션 2개 = 파티션을 하나씩 나눠 소비 |
